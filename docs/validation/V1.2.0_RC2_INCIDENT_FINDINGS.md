# v1.2.0 RC2 incident findings

Date: 2026-08-08
Source: user-supplied `Data/logs/content_agent.log` from the working portable installation.

## LinkedIn duplicate incident confirmed

Package `#98`, target `#364`, platform `linkedin` was submitted three times:

- 2026-08-07 16:00:30 Kyiv-local application log sequence: first LinkedIn attempt, then `Unexpected content type: <missing>`.
- 2026-08-07 16:15:38: second LinkedIn attempt, same error.
- 2026-08-07 16:45:40: third LinkedIn attempt, same error.

Facebook, Threads and Telegram targets from the same package were marked sent and were not repeated. The duplicate risk therefore came from LinkedIn never reaching `target.status=sent` even though LinkedIn could already have accepted each create request.

The same LinkedIn error also appears in earlier log history for packages `#35`, `#44` and `#56`, confirming this is not a one-off network event.

## Root cause

The generic `fetch_url()` content-type gate rejected a successful LinkedIn create-post response when the response had no `Content-Type` header. LinkedIn can legitimately return an empty success response while carrying the created post ID in `x-restli-id`. The exception occurred before the publisher could inspect that header, so the queue treated the target as retryable and issued another create POST.

## RC2 fix

- LinkedIn create-post uses a LinkedIn-specific response parser that accepts an empty 2xx response without Content-Type.
- The created post ID is read from `x-restli-id` or response JSON when present.
- A durable `linkedin_write_started` marker is saved before create POST.
- A durable `linkedin_post_id` and `linkedin_write_completed` marker are saved before target status is flipped to sent.
- If the result becomes ambiguous after the write barrier, the target becomes `outcome_unknown`, automatic retry is disabled, and subsequent resume cannot issue another LinkedIn create POST.

## Threads UNKNOWN incidents

The supplied log also contains repeated literal `UNKNOWN` errors for Threads, including packages `#89`, `#95`, `#100` and `#103`. RC2 converts a literal UNKNOWN PublishError into a descriptive non-retryable failure so the queue stops blind repetitions and shows an actionable reason.

## Media 404

The screenshot supplied separately showed a `cdn4.telesco.pe` JPEG candidate returning HTTP 404. That UI-side asynchronous media error was not present in the file log, which confirms the need for additional media logging. RC2 logs discovery/download failures, prioritizes real video over poster/thumbnail candidates, and refreshes the source once after a selected media candidate returns HTTP 404.
